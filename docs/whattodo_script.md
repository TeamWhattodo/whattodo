# WhatToDo 발표 대본

> **발표 대상**: AI 에이전트 실무자 과정 수강생 및 강사
> **총 발표 시간**: 발표자 조절
> **발표 흐름**: 문제 → 팀 구성 → 아키텍처 4단계 진화(핵심) → 기술 선택 → RAG → 성능 평가 → 배운 것 → 마무리

---

## 0. 인트로

안녕하세요. WhatToDo 팀입니다.

저희 서비스 이름이 "WhatToDo"인데, 직역하면 "뭐 해야 하지?"입니다.
이 이름이 프로젝트 전체를 가장 잘 설명합니다.

잠깐 상상해보세요.
3일 휴가를 다녀왔습니다.
다음 날 출근하면 이메일 47통, 슬랙 멘션 213개, Jira 알림 8건.
"뭐부터 봐야 하지?"라는 생각이 드는 순간, 오전이 끝납니다.

WhatToDo는 이 문제를 해결합니다.
앱을 열면, **60초 안에 긴급한 것부터** 알려줍니다.

## 1. 팀 구성

5인 팀입니다.

- **고인범** — 팀장. 기획, 에이전트 핵심 루프, 발표·문서
- **김현진** — 디자인·UX, 프론트엔드 개발 (React 전환, 세션 관리)
- **김태훈** — 백엔드 개발·고도화 (성능 평가, 브리핑·리포트 에이전트 프롬프트)
- **신현섭** — 백엔드 개발·고도화 (PostgreSQL 마이그레이션, APScheduler, Docker)
- **정원이** — 개발·고도화 (action_agent CRUD, HitL, 사내 규정 문서 관리)

중요한 건, 프로젝트 첫날 **`WorkItem` 스키마 하나를 합의로 확정**했다는 점입니다.
이 스키마 하나 덕분에 각자 독립적으로 개발하면서도 결과물이 연결됐습니다.

"인터페이스 합의가 병렬 개발의 핵심이다"는 걸 이 경험에서 직접 확인했습니다.

## 2. 아키텍처 진화 — 핵심

오늘 발표의 핵심입니다.

저희 아키텍처는 **4단계에 걸쳐 진화**했습니다.
각 단계는 이전 단계의 한계를 직접 겪고 나서 자연스럽게 다음 단계로 넘어갔습니다.

```
1단계 → 고정 워크플로우   LLM 없음, 함수 파이프라인
2단계 → 단일 에이전트     LLM이 순서를 결정
3단계 → 키워드 Router     의도 분류 후 전담 SubAgent
4단계 → Supervisor + ReAct  Orchestrator가 SubAgent를 tool로 호출
```

하나씩 설명하겠습니다.

---

### 1단계 — 고정 워크플로우

*(다이어그램: arch_phase1.png)*

LLM이 전혀 없습니다.
`fetch_emails` → `score_urgency` → `classify_items` → `write_report`
이렇게 고정된 순서로 함수가 실행됩니다.

"그러면 왜 이게 1단계로 필요했냐?"

이유는 두 가지입니다.

첫째, **`WorkItem` 스키마가 실제로 팀 전체를 연결하는지 검증**해야 했습니다.
mock 데이터를 넣었을 때 파이프라인이 끝까지 돌아가면, 팀원들이 만든 각 부분이 호환된다는 뜻입니다.

둘째, LLM을 에이전트로 올리기 전에 **LLM 응답 형식 자체를 파악**해야 했습니다.
이 시기에 LLM을 `messages.create`로 직접 호출했습니다.
"이 항목들을 분류해줘"라고 보내면 어떤 포맷으로 돌아오는가,
파싱이 어떻게 깨지는가를 먼저 이해하고 나서야 tool_use 루프를 만들 수 있습니다.

에이전트가 잘못 동작했을 때 "LLM 판단 문제인가, tool 로직 문제인가"를 분리하려면
파이프라인이 먼저 정확하게 동작해야 합니다.

---

### 2단계 — 단일 에이전트

*(다이어그램: arch_phase2.png)*

핵심 변화는 **"코드가 순서를 정하는 것"에서 "LLM이 순서를 정하는 것"으로의 전환**입니다.

"정산 리포트 작성해줘"라고 하면,
에이전트가 스스로 fetch → parse → compute → write_report 순서를 결정합니다.

이 단계에서 Gmail, Calendar 실데이터가 들어오기 시작했습니다.
보고서 PDF 생성, 맞춤법 검사 tool도 추가됐습니다.

그런데 **한계**가 생겼습니다.

tool이 15개를 넘어서자 선택 정확도가 낮아졌습니다.
"메일 답장 써줘"라고 했을 때 관련 없는 Jira tool을 호출하거나,
불필요한 중간 단계를 삽입하는 경우가 늘었습니다.

**tool이 많아질수록 LLM의 선택 공간이 넓어지고, 선택 오류 확률도 높아진다**는 사실을 확인했습니다.

---

### 3단계 — 키워드 Router + 전담 SubAgent

*(다이어그램: arch_phase3.png)*

해결책으로 **의도를 먼저 분류**했습니다.

`intent_classifier`가 키워드 매칭 + LLM으로 "브리핑 요청"인지, "보고서 요청"인지, "액션 요청"인지를 먼저 판단합니다.
그 다음 해당 도메인 전담 SubAgent로 라우팅합니다.

각 SubAgent는 자기 도메인 tool만 갖습니다.
Briefing Agent, Report Agent, Action Agent, Search Agent.
Slack 발송, Jira 업데이트, Notion 수정, Calendar 이벤트 생성·삭제까지
전 서비스 CRUD가 이 단계에서 완성됐습니다.

그런데 **또 한계**가 나왔습니다. 세 가지였습니다.

첫째, "fetch 결과를 report에 넘겨라"처럼 **에이전트 간 결과 전달**이 필요할 때
graph edge를 수동으로 추가해야 했습니다.

둘째, SubAgent 결과가 다음 SubAgent 입력으로 쓰이지 않았습니다.

셋째, "수집 실패 시 부분 진행" 같은 **동적 판단을 정적 그래프로는 표현할 수 없었습니다.**

라우팅은 해결됐지만, 에이전트 간 협력이 막혔습니다.

---

### 4단계 — Supervisor + ReAct 패턴 (현재)

*(다이어그램: arch_phase4.png)*

지금의 구조입니다.

크게 다섯 레이어로 설명할 수 있습니다.

**① 외부 서비스**: Gmail, Slack, Jira, Notion, Calendar

**② 백그라운드 워커**: APScheduler가 2~15분 주기로 각 서비스에서 데이터를 가져옵니다.
SDK를 직접 호출하고, LLM이 raw 내용을 요약하고, deadline을 ISO 형식으로 추출해서 PostgreSQL에 저장합니다.

**③ 데이터 레이어**: PostgreSQL + pgvector.
work_items, 대화 이력, 규정 문서 벡터, 사용자 인증 정보가 모두 PostgreSQL 하나에 들어갑니다.

중요한 설계 결정: `urgency_level`은 DB에 저장하지 않습니다.
조회 시점에 `deadline - now`로 실시간 계산합니다.
어제 저장된 "긴급도 3"은 오늘 조회하면 "긴급도 7"이 돼야 합니다.
저장된 값은 갱신 주기에 묶이지만, 계산하면 항상 정확합니다.

**④ Agent 서비스**: Supervisor + 5개 SubAgent.

Supervisor는 `create_react_agent`로 만들어진 ReAct 에이전트입니다.
SubAgent들이 이 Supervisor의 **@tool**로 등록돼 있습니다.

"브리핑 하고 보고서도 만들어줘"라는 요청이 오면
Supervisor가 스스로 판단해서 fetch_agent를 먼저 호출하고,
그 결과를 briefing_agent에 넘기고,
마지막으로 report_agent를 호출합니다.

**3단계에서 graph edge로 수동으로 연결해야 했던 것이,
4단계에서는 프롬프트 규칙으로 자동 성립합니다.**

**⑤ UI**: React 19 + Vite. 현재 어떤 에이전트가 동작 중인지 표시하고,
완료 후 invoke 형식으로 전체 결과를 한 번에 반환합니다.

## 2-5. SubAgent 상세

4단계 아키텍처에서 Supervisor 아래 다섯 개의 SubAgent가 있습니다.
각각 어떤 역할을 하고, 어느 정도 완성됐는지 솔직하게 말씀드리겠습니다.

---

### fetch_agent — 안정적

가장 기반이 되는 에이전트입니다.

Gmail, Slack, Calendar, Jira, Notion에서 수집된 항목을 **DB에서 조회**합니다.
실제 API 호출은 백그라운드 워커가 이미 처리했으므로, fetch_agent는 PostgreSQL SELECT만 실행합니다.

핵심은 응답 시 **긴급도를 실시간 계산**한다는 점입니다.
저장된 `deadline`과 현재 시각을 비교해서 1~10점 긴급도를 계산하고,
구조화된 JSON으로 반환합니다.

fetch → briefing 흐름이 가장 안정적으로 동작합니다.

---

### briefing_agent — 안정적

fetch_agent가 가져온 데이터를 받아서
**긴급 / 중요 / 일반 3단계 마크다운 브리핑**으로 정리합니다.

특이한 점은 tool이 전혀 없다는 것입니다.
LLM 단일 호출로 처리하기 때문에 빠르고 안정적입니다.

"3일 쉬고 왔어. 뭐 쌓였어?"라는 요청에
Supervisor가 fetch_agent → briefing_agent 순서로 호출하면
🔴 긴급 3건 / 🟡 중요 7건 / 🟢 일반 180건 같은 형태로 출력됩니다.

---

### search_agent — 안정적

두 가지 검색을 담당합니다.

첫째, **DB 항목 검색**: "지난주 박팀장이 보낸 Slack 메시지 있어?" 같은 질문에 답합니다.

둘째, **사내 규정 RAG**: pgvector 기반 의미 검색으로 규정집 관련 질문을 처리합니다.
"해외 출장 일비 규정 얼마야?"라고 하면 계층적 청킹으로 저장된 규정 문서에서 답을 찾아옵니다.

이 부분은 이후 RAG 섹션에서 더 자세히 설명하겠습니다.

---

### report_agent — 부분 완성

주간·월간 업무 보고서, 경비 정산 리포트를 생성합니다.

파일 업로드·파싱·PDF 출력까지는 동작합니다.
영수증 이미지나 텍스트를 올리면 날짜, 가맹점, 금액, 카테고리를 자동 추출하고,
사내 규정 RAG와 연동해 "식대 3만2천원이 규정 한도 3만원을 초과합니다"까지 검증합니다.

다만 **복잡한 정산 시나리오**에서 간헐적으로 LLM 판단 오류가 발생합니다.
항목이 많거나 규정 예외 케이스가 섞이면 계산이 틀리는 경우가 있습니다.

---

### action_agent — 기능은 있으나 불안정

가장 범위가 넓고 가장 미숙한 에이전트입니다.

Gmail 발송·삭제, Slack 메시지 발송·삭제, Jira 이슈 생성·상태변경·댓글,
Notion 페이지 CRUD, Calendar 이벤트 관리까지 **25개 tool**을 갖습니다.

문제는 tool이 많아지면서 생기는 선택 오류입니다.
"박팀장 Slack DM 답장 보내줘"에서 source_id를 잘못 파싱하거나,
스레드 답글이 아닌 새 메시지로 발송하는 경우가 있습니다.

파괴적 액션(발송·삭제)은 **HitL로 코드에서 강제 차단**하고 있어
오작동이 실제 피해로 이어지는 건 방지하고 있습니다.
하지만 "원하는 대로 한 번에 실행된다"는 신뢰도는 아직 부족합니다.

2단계에서 "tool이 많아질수록 선택 오류가 늘어난다"고 배웠는데,
action_agent에서 똑같은 문제를 다시 마주쳤습니다.
개선 방향은 25개 tool을 도메인별로 쪼갠 하위 에이전트로 나누는 것입니다.

## 3. 기술 선택과 이유

### MCP → SDK 직접 호출

초기에 Slack, Jira, Notion을 MCP로 연결했습니다.

실제로 겪은 문제는 두 가지였습니다.

첫째, **출력 형식이 비결정적**이었습니다.
같은 Slack 메시지를 조회해도 때로는 JSON, 때로는 자연어 설명이 섞여 돌아왔습니다.
에이전트가 이 결과를 파싱해야 하는데, 형식이 불규칙하면 tool call 결과를 신뢰하기 어렵습니다.

둘째, **프로세스 불안정**이었습니다.
MCP stdio 방식은 별도 프로세스를 띄웁니다.
프로세스가 죽으면 에이전트가 무한 대기 상태에 빠졌습니다.

SDK 직접 호출로 바꾸면서 `slack_sdk`의 `{"ok": true, "ts": "..."}` 같은 고정된 구조를 에이전트가 받게 됐습니다.
**tool 결과가 예측 가능해지면서 tool call 정확도가 올라갔습니다.**

### DB 레이어의 역할

SDK로 전환하면서 새 문제가 생겼습니다.
매 대화마다 Gmail API, Slack API를 실시간 호출하면 응답 시간이 수 초씩 걸립니다.

이를 해결하기 위해 백그라운드 워커 + DB 레이어를 추가했습니다.
워커가 주기적으로 수집해서 저장하고, 에이전트는 DB를 조회합니다.
이 전환으로 체감 지연 시간이 대폭 감소했습니다.

### HitL — 코드로 강제

파괴적 액션(이메일 발송, Slack 메시지, Jira 수정)은
LangGraph의 `interrupt()`로 실행을 중단하고 사용자 확인을 받습니다.

중요한 것은 이 체크가 **Python 코드로 강제**된다는 점입니다.
프롬프트 지시만으로는 LLM이 무시할 수 있습니다.
코드가 막아야 안전합니다.

## 4. RAG 실험

### 왜 계층적 청킹인가

사내 규정 검색을 위해 Ragas 프레임워크로 5가지 청킹 전략을 평가했습니다.
fixed / recursive / structure / semantic / hierarchical.

수치 차이는 크지 않았습니다. Context Precision·Recall 모두 0.88~0.90대로 유사했습니다.

그러면 왜 계층적 청킹을 선택했냐?

수치가 아니라 **문서 구조와의 적합성** 때문입니다.

사내 규정 문서는 이런 구조를 갖습니다.

```
3장. 출장 여비 규정
  3.1절. 교통비 지급 기준
    3.1.1. 근무지 내 출장 시
      - 편도 20km 미만: 10,000원
```

고정 크기로 자르면 "10,000원"만 검색되고, 이 금액이 어느 조건인지 맥락이 사라집니다.

계층적 청킹은 두 종류의 청크를 만듭니다.
- **Child 청크** (150자): 조항 단위 — 벡터 검색에 사용
- **Parent 청크** (1500자): Child가 속한 챕터 전체 — LLM에 전달

"출장 교통비 한도"를 물으면 Child(3.1.1 조항)로 검색하고,
그 조항이 속한 3.1절 전체를 LLM에 전달합니다.
숫자와 조건이 함께 전달되어 맥락 있는 답변이 나옵니다.

### 파라미터 튜닝

8대 조합(V1) → 9대 정밀 조합(V2)으로 두 차례 실험했습니다.
결론은 **Parent 1500자 × Child 150자** 조합이었습니다.

V1·V2 모두에서 Context Precision과 Faithfulness가 가장 높았습니다.
Parent가 너무 작으면 맥락이 부족하고,
Child가 너무 크면 검색 정밀도가 떨어졌습니다.

## 5. 성능 평가

### 평가 방법론

NeurIPS 2025에 발표된 TheAgentCompany 논문의 방법론을 참고했습니다.

이 논문의 핵심 아이디어는 **체크포인트 기반 부분 점수**입니다.
태스크를 완전히 수행하지 못해도, 완료된 중간 단계만큼 점수를 인정합니다.

저희는 이 방법론을 WhatToDo 도메인에 직접 구현했습니다.
12개 시나리오, 5개 카테고리, 각 시나리오마다 3~5개 체크포인트.

한 가지 명확히 짚고 넘어가겠습니다.
저희 결과와 논문 수치를 직접 비교하는 건 의미가 없습니다.
논문은 "채용 후보 스크리닝 후 면접 일정 잡기" 같은 27+ 단계 장기 태스크 175개를 평가합니다.
저희는 "최근 메일 3개 요약해줘" 같은 단발성 대화 태스크 12개입니다.
**방법론(체크포인트 기반 부분 점수)을 참고했을 뿐, 수치는 다른 난이도 기준입니다.**

### 핵심 결과

*(차트: whattodo_eval_chart.png)*

프로젝트 초기에 설정한 성공 기준은 "체크포인트 통과율 50% 이상"이었습니다.
결과적으로 **gpt-4o-mini 기준 75%**로 목표를 초과 달성했습니다.

**gpt-4o-mini가 gpt-4o를 앞섰습니다.**
Success Rate 기준 75% vs 41.7%.

에이전트 태스크에서 모델 크기와 성능이 비례하지 않습니다.
gpt-4o는 tool 호출 패턴보다 과도하게 추론하는 경향이 있어,
단순 액션 수행에서 오히려 실수가 많았습니다.
**구조화된 tool use 태스크에서는 작고 명확하게 따르는 모델이 유리합니다.**

복합 의도 시나리오(S11: "브리핑 하고 보고서도 만들어줘")에서 차이가 가장 컸습니다.
gpt-4o 0.30 vs gpt-4o-mini 1.00.
gpt-4o는 두 번째 에이전트 호출을 생략하고 응답을 완료하는 경향이 있었습니다.

공통 약점은 S4 Jira와 S9 Notion이었는데,
이건 모델 문제가 아니라 인프라 문제였습니다.
평가 시점에 Jira 연동이 불안정했고, Notion API 토큰이 만료돼 있었습니다.

**평가 시스템이 "모델 판단력 문제"와 "시스템 연동 문제"를 분리해서 보여준다는 점에서
평가 파이프라인 자체의 가치가 확인됐습니다.**

두 모델 모두 Tool Call Accuracy는 100%였습니다.
어떤 에이전트를 불러야 하는지는 Supervisor가 완벽하게 판단했습니다.

### 응답 시간

정량 모니터링은 완료하지 못했습니다만, 체감 기준으로 확인한 수치입니다.
- 단순 작업 (브리핑, 단일 검색): 20~30초
- 복합 작업 (브리핑 + 보고서, 경비 정산): 1분 내외

DB 레이어 도입 이후 체감 지연 시간이 명확하게 감소했습니다.
외부 API 응답 대기가 PostgreSQL SELECT로 대체됐기 때문입니다.

## 6. 배운 것들

개발하면서 배운 것을 요약하면 이렇습니다.

**첫째, 인터페이스 합의가 병렬 개발의 핵심입니다.**
`WorkItem` 스키마 하나가 6명의 독립 개발을 가능하게 했습니다.

**둘째, MCP는 내부 지식 기반에, SDK는 실시간 서비스 연동에 맞습니다.**
어떤 방식이 항상 옳은 것이 아니라, 연결하는 대상에 따라 선택이 달라집니다.

**셋째, 프롬프트보다 코드로 강제하세요.**
파괴적 액션을 프롬프트 지시로만 막으려 하면 LLM이 무시할 수 있습니다.
Python 코드로 실행 전에 차단하는 것이 훨씬 안전합니다.

**넷째, 정적 그래프의 한계를 일찍 발견하세요.**
키워드 Router는 단일 에이전트보다 정확했지만,
에이전트 간 결과를 넘기는 흐름이 필요해지자 한계가 드러났습니다.
Supervisor 패턴이 동적 흐름에 더 맞는 선택이었습니다.

**다섯째, 도구가 많다고 능력이 늘지는 않습니다.**
action_agent는 25개 tool을 갖지만, tool이 많을수록 선택 오류가 증가했습니다.
범위가 좁고 명확한 SubAgent가 범용 에이전트보다 예측 가능합니다.

**여섯째, 저장 vs 계산을 구분하세요.**
긴급도를 저장하면 갱신 주기에 묶입니다.
"계산이 항상 정확한 것"은 저장보다 낫습니다.

**일곱째, 평가 없이 개선할 수 없습니다.**
"왠지 더 잘 되는 것 같다"는 느낌이 아니라
Success Rate, Tool Call Accuracy 같은 정량 지표로 확인해야 합니다.

## 7. 마무리

WhatToDo는 4주 만에 기획부터 멀티에이전트 시스템까지 구현한 프로젝트입니다.

아키텍처는 4단계에 걸쳐 진화했습니다.
고정 워크플로우의 경직성,
단일 에이전트의 tool 선택 오류,
키워드 Router의 체인 불가 문제를
차례로 해결하다 보니 Supervisor + ReAct 패턴에 도달했습니다.

### 애로 사항

개발 과정에서 가장 힘들었던 부분은 **외부 API별 응답 포맷 차이**였습니다.
Slack, Jira, Notion, Gmail 각각이 서로 다른 형식으로 데이터를 반환하는데,
에이전트가 이걸 일관되게 해석하도록 만드는 파싱 로직이 예상보다 훨씬 복잡했습니다.
이게 결국 MCP → SDK 직접 호출로 전환한 가장 큰 이유이기도 합니다.

팀원이 5명이다 보니 **역할 경계 설정**도 쉽지 않았습니다.
같은 기능을 두 명이 동시에 건드리는 충돌이 생기기도 했고,
누가 어디까지 책임지는지 명확히 하는 데 시간이 걸렸습니다.

### 아쉬운 점

초반부터 5개 SubAgent를 모두 구현하려다 보니 완성도 면에서 아쉬운 부분이 남았습니다.
action_agent의 불안정함이 대표적입니다.
돌이켜보면 **핵심 기능 하나를 깊게 파는 방향**이 더 나았을 수 있습니다.
브리핑과 search_agent 두 개만 완벽하게 만들었다면 더 신뢰도 높은 시스템이 됐을 겁니다.

### 향후 계획

가장 먼저 할 것은 **긴급 업무 브리핑 응답 속도 개선**입니다.
현재 20~30초인 단순 작업 처리를 더 빠르게 줄이는 것이 목표입니다.
그 다음은 action_agent 파이프라인 고도화 — tool을 도메인별 하위 에이전트로 분리하는 것입니다.

---

AI 에이전트는 "뭔가 신기한 것"이 아닙니다.

사람이 반복적으로 하는 업무를 정확하게 식별하고,
그것을 tool로 분해하고,
LLM에게 언제 어떤 tool을 쓸지 판단하게 하는 것입니다.
그리고 그 판단이 틀릴 때 어떻게 통제할 것인지를 코드로 정의하는 것입니다.

이상입니다. 감사합니다.

## 예상 Q&A

**Q. 왜 Supervisor가 직접 DB를 조회하지 않고 fetch_agent를 거치나요?**

A. fetch_agent가 DB SELECT와 긴급도 실시간 계산을 하나의 인터페이스로 캡슐화하기 때문입니다. Supervisor 입장에서 "fetch_agent를 호출하면 구조화된 업무 목록이 온다"는 단순한 계약으로 동작합니다. 긴급도 계산 로직이 바뀌어도 Supervisor는 영향받지 않습니다.

**Q. gpt-4o-mini가 더 좋은 결과를 냈는데, 왜 처음부터 mini를 안 쓰나요?**

A. 에이전트 태스크는 모델 크기보다 "지시를 얼마나 명확하게 따르는가"가 더 중요합니다. 평가 결과를 보고 나서야 알게 됐습니다. "평가 없이 개선할 수 없다"의 직접 사례입니다.

**Q. action_agent가 불안정하다고 하셨는데, 어떻게 개선할 계획인가요?**

A. 단기적으로는 few-shot 예시를 추가해 tool 선택 패턴을 학습시키는 방향입니다. 장기적으로는 25개 tool을 기능별로 세분화한 SubAgent로 나누는 것을 검토 중입니다.

**Q. 백그라운드 워커 수집 주기와 실시간성 사이 트레이드오프는요?**

A. 현재 2~15분 주기로 수집합니다. 이 주기 안에 업데이트된 데이터는 다음 수집까지 반영되지 않습니다. 브리핑은 허용 가능한 지연이지만, action(발송, 생성)은 실시간 API 호출이 필요합니다. 이 분리가 백그라운드 워커(수집) + action_agent(실시간 쓰기)로 역할이 나뉜 이유입니다.

**Q. TheAgentCompany 논문 수치와 직접 비교가 안 된다고 하셨는데, 그러면 왜 같은 방법론을 썼나요?**

A. 체크포인트 기반 부분 점수 방식이 "완전 성공/실패"보다 에이전트 개선 방향을 더 잘 보여주기 때문입니다. "S11에서 두 번째 에이전트 호출을 안 한다"는 걸 Success Rate만 보면 알 수 없지만, Partial Score와 체크포인트별 결과를 보면 정확히 어디서 실패하는지 보입니다.
